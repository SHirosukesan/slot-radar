# SLOT RADAR — Claude開発用 統合仕様・実装計画

版: 1.0 / 2026-10-18 / 状態: 開発開始前・仕様引き継ぎ

> 最重要指示: Claudeはこの文書を **仕様の基準** とし、まず既存ファイル・GitHub権限・公開方式を確認する。全Phaseを一度に実装しない。各Phaseを「計画→小さなIssue→実装→テスト→PR→確認」の順で進める。実行できないGitHub操作を実行済みと宣言しない。

## 0. 開発ゴールと優先順位

SLOT RADARは、日本全国のパチスロ店舗・イベントを探し、信頼できる過去実績と個人的な現場感覚を区別して比較し、Googleマップで移動し、実戦・給与・親の損益も記録できるモバイル優先PWA。利用者は最初は本人一人。将来の拡張余地を保つ。

優先順位: (1) パッと見てわかるUI (2) 根拠・信頼度・欠損を正しく扱う (3) 動いて壊れない (4) 入力の少なさ (5) 維持費を抑える (6) 高度な自動化。実装可能性・法律・利用規約・費用を無視して「リアルタイム自動取得」などを約束しない。

別構想「SLOT PRO」（機種攻略/やめどき）の統合は現時点では実施しない。

## 1. 開発・GitHub運用

- GitHubに新規repo `slot-radar` を作る。利用者がGitHub操作をClaudeに任せたい意向。Claudeの接続が可能なら権限を確認して実施。不可なら **必要最小限のユーザー操作を1個ずつ**案内する。GitHub個人認証情報や復旧コードを要求しない。
- repo公開設定: **初期はPrivateを推奨**（未公開の仕様やデータを不用意に公開しない）。公開サイトが必要になった段階で、GitHub Pagesの公開要件・アカウントプラン・公開リポジトリ運用を検討。無料公開が優先なら、秘密情報を除去したうえでPublicへ移行するか、Cloudflare Pagesなどを比較する。GitHub Pagesは公開されたWebアプリの**個人の非公開DB**には使わない。
- `main`を動作確認済み、`feature/*`ブランチで変更、Pull Request、テスト完了後マージ。GitHub Issueに実装タスク・バグ・未確定仕様を登録。
- GitHub Actions: lint, typecheck, test, build（必要に応じPlaywright）。初期段階からCIを導入。デプロイはGitHub PagesのActions方式を第一候補にし、問題があれば理由と代替を相談する。
- 秘密鍵、APIトークン、個人収支、非公開LINEスクリーンショット、機微なデータをリポジトリにコミットしない。`.env.example`のみコミット。SecretsはGitHub ActionsのSecrets/環境変数に。CIに不要な広い書込権限を与えない。
- プロジェクト文書: README.md, CLAUDE.md, docs/product-spec.md, docs/decisions.md, docs/open-decisions.md, docs/architecture.md, docs/data-sources.md, docs/scoring.md, docs/roadmap.md, docs/changelog.md, docs/test-plan.md。
- 各PRの報告: 何を実装/未実装、確認方法、変更ファイル、テスト結果、費用・制約、次のIssue。簡潔な日本語で専門語に注釈。

## 2. 推奨アーキテクチャ

- TypeScript + React + Vite、CSSはTailwindなど最小の一貫したデザイントークン。PWAは後方互換・ブラウザ制約を考慮。
- ルーティング、コンポーネント、型、サービス、データソースアダプター、評価ロジック、同期層を分離。画面に生のスクレイピングを直接実装しない。
- Phase 1-3は**明示したサンプルデータ**とブラウザ内保存で動くように。ダミーデータを実データと誤認させない。
- 端末内保存: IndexedDB。オフライン実戦入力用イベントレコード、保存済み状態/同期キュー/競合検出を後から追加できる構造。
- 将来: Supabaseなど認証+DB+画像Storageを評価。RLS/アクセス制御、画像公開範囲、無料枠、データ移行、同期競合の検証を必須にする。
- データ取得: 公式サイト、許可されたAPI、公開店舗情報、正規に利用できる集計サイト、ユーザー持込画像/URL。取得元ごとに利用条件、取得可能範囲、失敗時フォールバック、取得頻度を管理。無断高頻度スクレイピングやログイン回避を実装しない。X・LINEへの自動アクセスを当然視しない。
- 日付時刻: 日本のローカル営業日・店舗ごとの閉店日跨ぎに注意。金額は整数円、メダルは枚数、レートは正確な有理数/小数で管理し丸め方を明記。

## 3. UI/UXの譲れない要件

- 暗色系（黒に近い背景）＋紫アクセント。**可読性・文字コントラスト最優先**。派手な多色は避ける。
- 店舗名・機種名、100点満点の重要数字を大きく。説明は短く補助的に小さく（ただし判読可能）。数値は桁を揃え、単位を明示。
- 一覧は数値中心、詳しい根拠は詳細画面に。タップ領域を大きく。お気に入りは星アイコン。表示項目のオン/オフを後から変更可。
- 店舗一覧では「総合」「設定狙い」「ハイエナ」を中心に表示。イベント評価は詳細に。データがなければ「— / 未評価」、0点にしない。
- 店舗一覧⇄地図表示切替。Googleマップで店舗位置確認・経路案内。店舗カード、詳細、お気に入りから直接経路を開ける。地図の埋込API費用は精査し、安価な方法を選ぶ。
- ナビ候補: ホーム/店舗検索/実戦記録/収支/お気に入り の下部5タブ。ただし画面が窮屈なら情報設計を改善して提案する。
- 検索画面ひとつに、並び順「おすすめ、総合、設定狙い、ハイエナ、穴場候補、更新、距離」。別の「穴場専用モード画面」は作らない。
- 並び順の昇順・降順（新しい順/古い順、高い順/低い順）、信頼度、更新日時、距離、イベント種別、営業日、時間帯等をフィルター。主要フィルター以外は折り畳む。地域・距離・信頼度など基本設定は永続化、一時フィルターは次回解除、任意の検索プリセット保存。
- 自宅/基本地域と一時的検索地点は概念として分離（詳細挙動は未決定）。初回に47都道府県から地域設定、その後変更可能。GPSは近隣店舗**候補提示のみ**、選択確定は本人。GPS拒否時は履歴・お気に入り・地域検索。
- 「今から行く」モードでは店舗自体の評価とは別に、移動時間・費用・到着後の狙いやすさを比較。Google Maps連携。リアルタイム空き台が不明なら「未確認」とする。Googleマップ混雑度≠スロット空き台・期待値台。

## 4. イベント機能

- **本日のイベント**。表示範囲は指定距離内 vs 全イベント（対象都道府県/地方/全国などの設計は調整可能）。初期設定した都道府県を基本にし、後から変更。
- 「まいったぁまいったぁ」は**優先監視・ホーム優先表示**。注目度は高くしても実績スコアにイベント名だけで無条件加点しない。お気に入りにしていない店舗の指定距離内重点イベントも見逃さない。
- 各イベント: 店舗、開催日、イベント種別、公式/第三者/不明/AI仮説、原典URLまたはアップロード画像、取得日時、開催確認状態、過去実績、対象機種の示唆候補、信頼度。
- イベントの強さは過去の実出玉・通常日との差・プラス台比率・データ取得率/新しさを見て算出。出玉≠設定確定。店舗全体と機種別を分ける。
- 同一イベントの過去開催を店舗単位で比較。「イベント別実績ランキング」を詳細に表示。通常日・土日祝・特定日を識別するが、属性は重なっても**営業日実績を二重計上しない**。
- AI注目機種の自動提案にユーザーの追加/除外/優先順を重ねる。AIの元順位と個人的順位は**別々に保存**。開催前の予測を保存し、開催後に事後的に書換えず検証可能にする。
- 重点イベント・お気に入りの重要告知を優先的にプッシュ/アプリ内通知。情報元へ直接遷移。通知の重複防止。PWA通知は端末・ブラウザの対応に注意。
- 重要度別更新: 重点イベントは3-6時間程度、お気に入りは6時間程度、一般店は1日1回、出玉は営業終了後を**設計目標**とする。ソース利用条件・コスト・実行環境の制約で実際の取得頻度が変わることを明示。取得失敗と新着なしを区別。

## 5. 分析・スコア・根拠

- 店舗の強さ、設定狙い、ハイエナ、イベントの過去実績、穴場候補、抽選競争/狙いやすさ、移動効率は異なる概念。**スコアを無根拠に合成しない**。採点根拠・重み・検証データが不足なら未評価。
- 店舗実績: 30日、90日、1年の比較。新しいデータに重み。同じイベントの履歴は別分析。情報の鮮度・件数・母数・欠損場所を信頼度に反映。
- 信頼度高を初期表示し、低信頼分析だけ隠せる。店舗や確認済み開催予定自体は隠さない。少数サンプルは暫定、極端な欠損は評価保留。
- 複数サイトが異なる場合は対象店舗、営業日、対象台数、集計時刻、計算方法を照合。異なる母集団を安易に平均しない。理由を解消できなければ競合値を出典付きで併記、該当評価は保留。
- 人気機種欠損など偏りを確認し、店舗全体と機種別で信頼度を別管理。
- 店舗ごとの現場感覚値: 客数、専業割合（推定）、狙い台の見つけやすさ、リセット多め/据え置き多め/混在/不明等。店舗単位で保存・修正。最終更新日を付ける。体感値と公開データは別保持、AIは根拠ある場合のみ見直し提案。勝手に体感値を書き換えない。
- 平均期待値、店舗の総設置台数、狙える台数、稼働/客数、専業vs一般客比率から立ち回り効率を考察。ただし「平均差枚=期待値」ではなく、公開データから断定できない値は推定または不明とする。
- AI自動重み付け⇄個人カスタム重み付けを切り替え。設定狙いとハイエナでは要因を別にする。
- 時間帯（朝/昼/夕方/夜）の分析は詳細で任意表示、データ不足の区画は評価保留。曜日/土日祝/特定日も別比較可能。
- 個人の実戦分析: 期待値台の発見効率、推定期待値、実現収支を別々に保持。単発の勝敗を期待値や店舗評価と混同しない。

## 6. 実戦記録・給与・親の損益

- 打ち子本人の実戦・給与・親（雇用主）損益を管理。グループ全体の人件費は不要。
- リアルタイムタイマー/後から入力・編集の双方。台移動ワンタップ、打った機種・台番号は後から補完可。勤務中=拘束時間、実遊技時間は別。台移動時や待機中は実遊技だけ停止して拘束を継続。その他時間=拘束−実遊技を自動集計、休憩・台探し・抽選待ち分類は任意。時間矛盾は警告し勝手に修正しない。
- 1勤務日に複数店舗、店舗切替簡単、最後にまとめて店舗別収支を記録。給与は勤務日につき原則1件で、店舗別配賦しない。
- 給与は日払いが基本、未払い・後日支払い可。拘束時給/遊技時給を表示。給与と台の差枚/実収支は別項目。
- 台別収支は任意、**店舗合計が優先**。直接最終収支を入力、または投資・回収から計算、円と枚両対応。現金貸出46枚/1000円、交換56枚/1000円など店舗固有で貸出・交換レートを別管理し有効日も保存。単純な20円/枚固定換算はしない。
- 親の店舗単位での結果報告を優先し、計算との差分を警告。親の1日損益=本人担当の店舗収支合計−本人給与（他経費が未登録なら「給与控除後の概算」と明記）。データがない場合の0補完は禁止。
- メダル受渡・持ちメダル残高管理は任意の高度機能。受け渡し自体は収益/損失に二重計上しない。相手先入力は任意。
- 複数端末同期時には一意ID、更新時刻、バージョン、競合処理を持つ。オフライン記録を端末内に確実に保存し、ネット復帰後同期。バックグラウンド常時稼働を前提にせず時刻差でタイマー復元。
- スクリーンショット等の画像は重要物のみ圧縮・クラウド保存。細文字/暗号は画質維持を選べる。原本保持は任意。非公開画像は本人だけが閲覧可能なStorageと権限で扱う。PWA Web Share Targetは対応端末のみ、アップロード代替必須。

## 7. 推奨データモデル（初期設計・適切に正規化）

- `shops`: ID、名称、住所、位置、都道府県、市区町村、Google Maps URL/Place ID、店舗状態
- `shop_machine_installations`: 店舗、機種、設置台数、適用開始/終了、出典
- `events`: ID、イベント名、説明、出典/種別
- `shop_event_occurrences`: 店舗、開催日、イベント、重複開催リンク、確認状態、出典
- `daily_shop_results`: 店舗、営業日、データ源、対象台数、平均差枚、合計差枚、プラス台比率、更新時刻、欠損数
- `machine_results`: 店舗、営業日、機種、台番号、差枚、稼働指標、出典
- `source_records`: URL、媒体、取得時刻、出典種別、掲載日、許諾/取得状況、保存した根拠
- `analysis_scores`: 対象ID、評価種別、期間、スコア/未評価、信頼度、母数、計算モデル版、根拠
- `user_shop_profiles`: 店舗ID、体感客数、専業推定、狙いやすさ、リセット傾向、記録日
- `favorites`, `user_preferences`, `saved_filters`
- `suggested_machines`, `user_priority_overrides`, `prediction_snapshots`
- `workdays`: 勤務開始終了、給与、支払状態、支払日
- `shop_sessions`: 勤務日、店舗、訪問時刻、店舗総収支、雇用主報告値
- `machine_sessions`: 店舗実戦、機種/台、開始終了、投資回収（任意）
- `time_segments`: 勤務日、遊技/その他、開始終了、任意分類
- `medal_transactions`, `exchange_rates`（任意機能）
- `sync_queue`, `sync_conflicts`, `attachments`（後期）

各データに`created_at`、`updated_at`、必要な範囲で`source_id`・可視性・データ由来（自動/手入力/推定）を付ける。データモデルの細部は実装時にER図を作成する。

## 8. フェーズ別ロードマップと完成条件

### Phase 0: GitHub・空のアプリ・CI/CD
1. GitHubアクセス可否確認→新規repo（必要ならユーザーの一操作を案内）
2. React+TS+Viteを初期化し、動作する初期画面、README、仕様書、CLAUDE.mdをコミット
3. Lint/typecheck/unit test/build CIをActionsで実行
4. 公開方式を確認、プレビューURLまたは動作方法を用意
**完了条件**: PR/コミットが存在、全チェック成功、PCブラウザで表示、手順がREADMEにある

### Phase 1: UI設計と店舗一覧（ダミー）
- デザイントークン・スマホ表示・共通レイアウト・下部ナビ・店舗カード（総合/設定狙い/ハイエナ）・未評価表示・詳細画面
**完了条件**: 文字・色が見やすい、スマホ横幅で崩れない、架空データ表示明示、画面遷移が正常

### Phase 2: 地域・検索・お気に入り・地図・Googleマップ
- 47都道府県、基準地点、距離指定、検索履歴、GPS候補表示と手動確定、並び替え、信頼度フィルター、プリセット、星登録、一覧/地図切替、Google Maps外部経路リンク
**完了条件**: 保存と再起動が正常、検索条件共有、GPS拒否でも使用可能、確認済みの住所への経路が開く

### Phase 3: イベント・今日のホーム
- 重点イベント、今日、距離/広域、開催情報、イベント名/店舗/日付、出典と信頼度、イベント詳細、同一開催重複表示の準備
**完了条件**: 今日の重点イベントが見られ、架空と実データの区別、フィルターで重要イベントを誤隠蔽しない

### Phase 4: データ取得・根拠・品質
- 出典台帳、正式に取得可能な実データソースの調査と1つ以上の取り込み、取得失敗、重複、差異、母数欠損、更新日時、キャッシュ
**完了条件**: 取得元の権利・制約を記録、出典クリック可能、同一条件でない数値を誤統合しない

### Phase 5: スコアリング・機種/イベント詳細
- 30/90/365日、機種別、イベント別ランキング、通常日差、暫定/保留、ルールに基づく説明可能なスコア、注目機種候補と予測履歴、店舗感覚値の登録
**完了条件**: テストデータで再現可能な計算、母数/出典/推定ラベル、欠損時の正しい挙動

### Phase 6: 実戦記録・給与・収支
- リアルタイム+後入力、台移動、拘束/遊技/その他、複数店、日給、未払、レート、差枚円換算、親の損益、グラフ
**完了条件**: 一日で複数店・複数台・後編集・未払い・非等価・不足値の試験が通る

### Phase 7: オフライン・クラウド・画像
- IndexedDB耐障害性、Supabase等の認証+RLS+Storage、差分同期・競合、スクショ圧縮/保存、OCR/AI候補抽出の承認フロー
**完了条件**: 圏外入力→復帰同期、二重登録なし、別端末で照合、非公開画像が他者に見えない

### Phase 8: 今から行く・通知・最適化
- 店舗スコアと移動コスト別表示、混雑体感・新鮮度、PWA通知の対応環境別動作、更新ジョブ優先度、性能・コスト監視
**完了条件**: 不明なリアルタイム情報を不明表示、イベント通知重複なし、主要画面レスポンス良好

### Phase 9: 運用・安定化
- 障害ログ、更新停止/取得失敗検知、ソース利用条件の定期確認、バックアップ/復元、無料枠監視、ユーザー向け操作説明、アクセシビリティ検査、セキュリティレビュー
**完了条件**: 更新が止まっても古いデータが最新と誤認されない、復旧方法が文書化されている

各Phaseは機能を独立した小Issueに分ける。新規データソースの難しさで全開発を止めない。

## 9. 未決定事項（実装を妨げない範囲で保留）

- 質問㉜: 打てなかった期待値台の記録方法。初期は任意欄としてスキーマ拡張余地のみ、UI必須化しない。
- 質問㊲: 同日複数イベントの寄与帰属。安全な暫定方針として複数タグと単一日次実績を記録し、因果効果の配分はしない。正式決定は分析前に確認。
- 質問㊴: ホーム地域と一時検索の保存ルール。初期設定地域は保存、検索先は一時状態として別管理する前提で実装前確認。
- 店舗評価点の正確な算出重み、しきい値、欠損許容度、低頻度イベント評価の統計手法。**サンプルの86点等を本番点数に流用しない**。実績データが揃うまで未評価・説明可能なルール基盤を優先。
- 全件網羅やSNS/LINE自動取得の可否は情報源ごとに調査・許諾確認。取得できない時は手動URL/画像入力を提供。
- Google Maps地図表示の技術（無料/料金、APIキー公開制限）、店舗位置データの入手手段、通知権限は実装前に評価。

## 10. 必須テストケース

1. 0件検索、GPS拒否、圏外、登録済みお気に入りのみ、信頼度不足でも店舗が消えない
2. 並び替え・フィルター保存/一時解除、プリセット復元、距離と都道府県切替
3. 公式イベントの開催事実とAI示唆の信頼度を分離、重点イベント優先表示
4. イベント重複日に日次出玉を二重集計しない、開催前予測を上書きしない
5. 別媒体の集計条件が異なる値を平均しない。高い取得率でも重要機種欠損を検知
6. 台移動中の拘束継続・遊技停止、実戦終了/後編集、ブラウザ再起動で時刻復元
7. 給与未払い、給与1日1回、店舗収支分離、親の報告と計算差異
8. 貸出/交換非等価、持ちメダル移動を収益に二重計上しない、未入力をゼロにしない
9. 同期競合・重複防止、秘密画像の権限制御、誤ったURL誘導防止
10. スマホの可読性、タップ領域、色覚/コントラスト、長い店舗名、省データ通信
